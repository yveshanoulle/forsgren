# CLAUDE.md — forsgren

Guidance for Claude Code in this repository.

## What this repo is

forsgren measures the four DORA metrics for a set of GitHub repositories from
data GitHub already has, and publishes them as a small static page (see
[README.md](README.md)).
It is written in Go: one module, `github.com/yveshanoulle/forsgren`.

## Layout

- `cmd/forsgren/` — the composition root; thin. `forsgren render --out <dir> [--config <path>] [--data <path>]` writes the site; with a config that lists no projects the page says so, and with the history as well it shows each project's deployment frequency and, from `commits.csv` next to `--data` (missing is none, unknown or malformed fails the render), its lead time for changes (`internal/metrics`, forsgren#16), and from the history its failed deployment recovery time (forsgren#17).
- `internal/config/` — `Load` reads and validates an installation's `forsgren.config.yml` (format version 1, strict YAML via `go.yaml.in/yaml/v3`); `forsgren check-config --config <path>` runs it, and `forsgren init-config --config <path>` writes the embedded starter (`starter.yml`) when the file is missing and keeps an existing one. Fixture configs only under `internal/config/testdata/`.
- `internal/history/` — the history format v1 (`data/deployments.csv`: a version line, a column line, one CSV line per deployment; README, History): `Load` reads it, `Append` creates it or appends only the deployments not yet there (key: repository, compared ignoring case, kind, ID), and refuses an unknown version or a malformed line untouched; `Validate` is its record check alone, writing nothing. `collect` appends to it; `render --data` reads it. Next to it the commits format v1 (`data/commits.csv`, one line per commit per deployment, for lead time, forsgren#16): `LoadCommits` and `AppendCommits`, the same rules (key: the deployment's key plus the SHA). Both files share one generic append-only CSV layer (`file.go`, `append.go`: a `format` per file). `Record.Stream` and `Chronological` (`stream.go`) are the stream and the order of deployments that `collect` and recovery time share (repository ignoring case, kind, name and task, releases one stream; created_at, then ID).
- `internal/github/` — the small GitHub REST client `collect` reads with (standard library only): deployments and their statuses, the default branch, a workflow's runs, releases, a tag's commit, and the commits between two SHAs (`Compare`, `compare/{base}...{head}`, oldest first, cut at the page limit or below `total_commits`; a base that is not an ancestor is `ErrNotAncestor`, a 404 or 422 `ErrMissingCommit`, both naming the two SHAs; forsgren#16; `collect` calls it); the token as a Bearer header only, `Link: rel="next"` pages up to a page limit, errors that name the repository (a 404 or 422 for a release's tag names the tag as missing, `ErrMissingTag`). Tests use `httptest` with fixtures in `testdata/`; they never touch the network.
- `internal/collect/` — `forsgren collect --config <path> --data <path>` (`cmd/forsgren/collect.go`, token from `FORSGREN_TOKEN`): per repository, its rule (`environment=`, `workflow=`, `release`) turned into history records, the final ones appended per repository, plus each newly stored successful deployment's commits since the previous success of its stream (repository, kind, name and task; releases one stream) in `data/commits.csv` next to `--data`, written before the deployments so a failed write loses no commits (`history.Validate` checks the deployments first); a success that finished after a newer success of its stream was stored gets none, with a warning, so no commit counts twice (forsgren#16; README, Collecting deployments). `metrics.yml` runs it daily.
- `internal/metrics/` — the DORA numbers, pure functions of the config's projects, the history records or stored commits and a render time passed in: `DeploymentFrequency` (successes in the last 7, 30 and 180 days, the latest date, and one of the six DORA Quick Check bands from `BandOf`, by average time between deployments on lead time's edges: the 30-day count decides, the 180-day count only when the 30 days hold none; shown with the deciding count and period by `BandText`, forsgren#16 step 6), and `LeadTimes` (forsgren#16: per project, the commits deployed in the last 30 days, each from author date to deployment, a negative one counted as 0; their median, the mean of the two middle ones for an even count, and their count; the six DORA bands of `LeadTimeBandOf`, a month being 30 days; shown by `LeadTime.BandText`, or "No lead time yet"), and `RecoveryTimes` (forsgren#17: per project, from the stored deployments only, each run of failures of a stream (collect's stream: repository ignoring case, kind, name and task; releases one stream) timed from its first failure's `created_at` to the next success's, one recovery per run, counted when the success is in the last 30 days; their median and count, banded by `LeadTimeBandOf`, since DORA's Quick Check gives failure recovery lead time's six answers; a run with no success yet counted as not recovered yet, whatever its age, never in the median; shown by `Recovery.BandText`, or "No failed deployments in the last 30 days").
- `internal/page/` — the page renderer: `Data.Projects`, one section per project (a `Project` is its `metrics.Frequency`, embedded, plus its `LeadTime` and its `Recovery`), numbers, durations and dates only, and with projects the render time as "Calculated 2026-10-03 12:00 UTC" (UTC to the minute, passed in as `now` is; none without `--data` or projects, forsgren#28), never a repository, SHA or commit message; `html/template` files embedded with `//go:embed`, shared chrome in `templates/layout/*.html` (one `{{define}}` each), one file per page in `templates/pages/*.html`, `styles.css`, the hand-authored `required-pages.json`, golden files in `testdata/` (placeholder, no-projects, no-data, frequency, lead time, recovery; `Scripts/check_golden_pages.sh` gates each).
- `Scripts/` — the gates, their self-tests and the build script; `Scripts/gate_report_order.txt` declares every gate.
- `.build/` — build output, never committed: `.build/bin/forsgren`, the generated site in `.build/site/`, the counts sinks.

## Build and quality gates

- **`./FBP.sh "<message>"`** (FBP = FullBuildAndPush) — the local run: `gofmt -w` → `./sfl.sh pre` → `./Scripts/build_site.sh` → `./sfl.sh post` → commit, and push only when everything is green. An ordinary red still commits locally with the subject `*** RED ****`; a secret-class red commits nothing. `./FBP.sh --no-commit` runs the gates and the build only.
- **`./sfl.sh pre|post`** — the gates of one phase, dispatched from `Scripts/gate_report_order.txt` (`label|script|phase|class`). Every gate is check-only here, as in CI, except npm audit's one-shot `npm audit fix` heal, whose lockfile change rides into the commit (CI turns that heal red).
- **`./Scripts/build_site.sh [out-dir]`** — builds `./cmd/forsgren` into `.build/bin/` and renders the site (default `.build/site`); writes the page count to `.build/site-page-count.log` only on full success.
- **`Scripts/fbp_agent_friend.sh "<message>"`** — FBP.sh under the agent-Friend commit identity, for the subagent loop.
- **CI** — `.github/workflows/quality.yml`, on every push to `main`, every pull request into `main` and by hand, on GitHub's hosted `macos-latest`: `Scripts/install_tools.sh` and `npm ci`, then `Scripts/run_ci_phase.sh pre` → `Scripts/build_site.sh` → `Scripts/run_ci_phase.sh post`, the same order-file rows as sfl, check-only. A `pull_request` trigger is allowed only on a workflow whose every job runs on a GitHub-hosted image label (`ubuntu-*`, `windows-*`, `macos-*`), never with a self-hosted runner; `Scripts/check_workflow_triggers.sh` is red otherwise. Never `pull_request_target`. `Scripts/test_quality_trigger_scope.sh` pins Quality's triggers and its `macos-latest`. See README, CI.
- **`.github/workflows/metrics.yml`** — the reusable workflow (`workflow_call` only) an installation's data repository calls daily with one line, `uses: yveshanoulle/forsgren/.github/workflows/metrics.yml@<commit> # vX.Y.Z`, the only version (no inputs): it `go install`s forsgren from its own `job.workflow_repository` at its own `job.workflow_sha` (checked as one owner/name and 40 hex first; `github.*` would be the caller's) on `go.mod`'s toolchain, checks out the caller's repository (pinned `actions/checkout`, `persist-credentials: false`), runs `forsgren init-config --config forsgren.config.yml` (a created starter is committed alone as `github-actions[bot]` and pushed to the branch the run is on, the token in git's environment only; a kept file exits 0 before any branch logic; the job has `contents: write`) and runs `forsgren check-config --config forsgren.config.yml` on it, failing the job with check-config's message (logged between `::stop-commands::<random token>` and `::<token>::`, so it never runs as a workflow command, and written to `$GITHUB_STEP_SUMMARY` after a cross mark) when the file is invalid, then runs `forsgren collect --config forsgren.config.yml --data data/deployments.csv` with the optional `FORSGREN_TOKEN` secret (`required: false`, passed by name by the caller, in that step's `env:` only; its output logged between `::stop-commands::` and its end like check-config's, its exit status kept as the output `status`), commits a changed `data/` alone as `github-actions[bot]` and pushes it like the starter (a branch that moved fails with an `::error`, never a rebase or force), renders (`--config`, `--data data/deployments.csv`), deploys to the caller's GitHub Pages, and last fails the job when collect failed; one run at a time per caller repository (`concurrency` on `github.repository`, `cancel-in-progress: false`). Nothing here runs it; `Scripts/test_metrics_workflow.sh` pins its shape. See README, Running forsgren.

Adding a gate: write the script and its self-test, give each a row in the order file at its canon position, add any Homebrew tool it needs to `Scripts/required_tools.txt`, describe it in README's Quality gates, and keep `Scripts/test_sfl_drives_from_order_file.sh` green (every `Scripts/test_*.sh` must be declared). README's "Working on forsgren" explains FBP.sh, sfl.sh and the order file.

- The plan and Yves's rulings for the bootstrap are on [#1](https://github.com/yveshanoulle/forsgren/issues/1).

## Code Health (CodeScene MCP), for every Go change

Adopted from MenoPower by Yves on 2026-10-02. An in-session check, deliberately not an sfl or CI gate.

- **Before the FBP of a Go change**, review the changed files with the CodeScene MCP (`code_health_review`, or `analyze_change_set` for several). Report each changed file's score in the hand-off.
- **Floor 9.0:** every Go file stays at 9.0 or above. Warn the moment a change would drop a file below it, and fix it before the FBP.
- **Scoreboard and ratchet:** [codescene-scores.json](codescene-scores.json) holds a row per Go file. `minScore` is the score minus 0.1 for a file below 10 (never below 9.0), and exactly 10.0 for a file at 10.0. Never drop a file below its `minScore`; lift it when a score improves. Update the rows of every reviewed file at each hand-off, and add a row for every new Go file.
- **Rules:** [.codescene/code-health-rules.json](.codescene/code-health-rules.json) puts the cyclomatic-complexity warning at 7 for all Go code, tests included, mirroring `.golangci.yml`'s gocyclo (min-complexity 6, tests included). Change both together.
- **On a Mac without the CodeScene MCP**, say so in the hand-off instead of a score. Never report a score from memory.

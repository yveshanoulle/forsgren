# CLAUDE.md — forsgren

Guidance for Claude Code in this repository.

## What this repo is

forsgren measures the five DORA metrics for a set of GitHub repositories from
GitHub data, and publishes them as a small static page (see
[README.md](README.md)).
It is written in Go: one module, `github.com/yveshanoulle/forsgren`.

## Layout

- `cmd/forsgren/` — the composition root; thin. `forsgren render --out <dir> [--config <path>] [--data <path>]` writes the site; with a config that lists no projects the page shows a how-to, and with the history as well it shows each project's deployment frequency and, from `commits.csv` next to `--data` (missing is none, unknown or malformed fails the render), its lead time for changes (`internal/metrics`, forsgren#16), and from the history its failed deployment recovery time (forsgren#17), and from the history with `failures.csv` next to `--data` (missing is none, unknown or malformed fails the render) its change fail rate (forsgren#18), and from the same files its deployment rework rate (forsgren#39), and from `issues.csv` next to `--data` (missing is none, unknown or malformed fails the render, `loadOrNone`) the days page's `Data.IssueDays` = `metrics.IssueDays(events, now, issueDays)` (30 days) and the issues page's `Data.IssueRows` = `metrics.IssueRows(events, now)` (`withHistory` in `render.go`; forsgren#76, #89, #123, #128); `render --latest <version>` makes the footer name a newer forsgren release, and `forsgren latest-release` (`latest.go`) prints forsgren's own latest release for it, silent and exit 0 when the lookup fails (forsgren#40), and `render --waiting-pr <number>` with `forsgren waiting-pull-request --version <x.y.z>` (`waiting.go`: the open pull requests of `GITHUB_REPOSITORY` with the job token, `github.ForsgrenBump`) name Dependabot's open pull request for it instead of "is available"; a 403 (no `pull-requests: read`) or any failure prints nothing and exits 0, and with `--status <path>` writes how it went (`ok`, `no-access`, `rate-limited` for GitHub's rate limit, which `OpenPullRequests` keeps as `ErrRateLimit`, never `ErrPullRequestsDenied`, or `failed`); `render --waiting-pr` below 1 is a usage error, and a negative `SOURCE_DATE_EPOCH` fails the render; `forsgren run-summary` (`summary.go`) prints the run's job summary markdown from `--latest`, `--waiting-pr`, `--pr-check` and `--repository` (the pull request is linked: a run page is private, unlike the page), and the workflow appends it to `$GITHUB_STEP_SUMMARY` without ever failing the run (forsgren#40). `forsgren check-needs --config <path> --repository <owner/name> [--status <path>]` (`checkneeds.go`, `setupissue.go`) checks what the running version needs (`internal/needs`) at the checkout root and opens, updates, reopens or closes the installation's one setup issue with the job's token (`GITHUB_TOKEN`), exit 0 whatever the write did; `--status` writes `ok`, `no-access`, `rate-limited` or `failed`, nothing missing is `ok` even when a close failed, and `run-summary --needs-check` and `render --needs-check` take it for the job summary's Setup line and the footer's "needs more configuration" (`Data.NeedsMore`, forsgren#73).
- `internal/config/` — `Load` reads and validates an installation's `forsgren.config.yml` (format version 1, strict YAML via `go.yaml.in/yaml/v3`; the optional per-repository `label` or `services` (task → label) name the page's sub-rows, `labels.go`, forsgren#38); the optional top-level `view:` (`standard`, `numbers` or `scoring`, `Config.View` as written, empty when absent, `checkView` in `validate.go`; the root page follows it, forsgren#46); `forsgren check-config --config <path>` runs it, and `forsgren init-config --config <path>` writes the embedded starter (`starter.yml`) when the file is missing and keeps an existing one. Fixture configs only under `internal/config/testdata/`.
- `internal/history/` — the history format v1 (`data/deployments.csv`: a version line, a column line, one CSV line per deployment; [docs/data-files.md, History](docs/data-files.md#history)): `Load` reads it, `Append` creates it or appends only the deployments not yet there (key: repository, compared ignoring case, kind, ID), and refuses an unknown version or a malformed line untouched; `Validate` is its record check alone, writing nothing. `collect` appends to it; `render --data` reads it. Next to it the commits format v1 (`data/commits.csv`, one line per commit per deployment, for lead time, forsgren#16): `LoadCommits` and `AppendCommits`, the same rules (key: the deployment's key plus the SHA). And the failures format v1 (`data/failures.csv`, one line per state of a `failure`-labelled issue: repository, issue number, opened_at, closed_at and failure_start, the last two possibly empty; for change fail rate, forsgren#18): `LoadFailures` gives each issue once, as its newest line says, and `AppendFailures` appends a line when an issue (key: `IssueKey`, repository ignoring case and number, which collect keys the issues it holds by too) differs from its newest line (`Failure.Revises`), so a closed or reopened issue is written again (the format's `revises`). `data/issues.csv` (`LoadIssueEvents`, `AppendIssueEvents`, `issueevents.go`; issues format v1, `repository,issue,event,reason,at`, the events and reasons as `history.Event*` and `history.Reason*` constants, the issue keyed by `IssueKeyOf` as the failures file keys it: one line per event of an issue of any label, `created`, `closed` with a reason `completed`, `not_planned`, `duplicate` or empty, or `reopened`, at in UTC to the second; an event is held when repository (ignoring case), issue, event and time match; forsgren#76). `data/issue_bugs.csv` (`LoadIssueBugs`, `AppendIssueBugs`, `issuebugs.go`; issue bugs format v1, `repository,issue,bug`, `IssueBug`, `bug` `true` or `false`, the newest line per issue by `IssueKey` wins and an issue gets a new line only when its flag changes, the format's `revises`; forsgren#126) says which issues carry the `bug` label; `IssueEvent.Bug` is an in-memory flag, not a column of `issues.csv`, set by `render` from this file. The files share one generic append-only CSV layer (`file.go`, `append.go`: a `format` per file). `Record.Stream` and `Chronological` (`stream.go`) are the stream and the order of deployments that `collect` and recovery time share (repository ignoring case, kind, name and task, releases one stream; created_at, then ID).
- `internal/github/` — the small GitHub REST client `collect` reads with (standard library only): deployments and their statuses, the default branch, a workflow's runs, releases, a tag's commit, a repository's open pull requests (`OpenPullRequests`, a 403 named as the missing `pull-requests: read`, `ErrPullRequestsDenied`; `ForsgrenBump` finds Dependabot's bump of forsgren's pin to exactly a version by its author and head branch, never its title, a temporary heuristic for the template's dependabot.yml (forsgren#42); forsgren#40), a repository's latest release (`LatestRelease`, no `Authorization` header when the token is empty, forsgren#40), and the commits between two SHAs (`Compare`, `compare/{base}...{head}`, oldest first, cut at the page limit or below `total_commits`; a base that is not an ancestor is `ErrNotAncestor`, a 404 or 422 `ErrMissingCommit`, both naming the two SHAs; forsgren#16; `collect` calls it); the issues labelled `failure` of a repository updated since a time (`FailureIssues`, `issues?labels=failure&state=all&since=`, pull requests left out, every page up to the limit; forsgren#18), each with its number, `created_at`, `closed_at` and the record block of its body (`failure-start:`, `failed-build:`, `fixed-build:` lines; a time it cannot read is zero); every issue of a repository whatever its labels (`Issues`, `issues?state=all&since=`, no `labels`, pull requests left out, every page up to the limit, sharing `FailureIssues`' paging; `AllIssues`, the same without `since` up to `FullReadMaxPages`; forsgren#76, and `BugIssues`, `labels=bug&state=all` without `since` up to `FullReadMaxPages`, forsgren#126), each with its number, `created_at`, `closed_at`, `state` and `state_reason` (null is empty); the token as a Bearer header only, `Link: rel="next"` pages up to a page limit, errors that name the repository (a 404 or 422 for a release's tag names the tag as missing, `ErrMissingTag`). Tests use `httptest` with fixtures in `testdata/`; they never touch the network.
- `internal/collect/` — `forsgren collect --config <path> --data <path>` (`cmd/forsgren/collect.go`, token from `FORSGREN_TOKEN`): per repository, its rule (`environment=`, `workflow=`, `release`) turned into history records, the final ones appended per repository, plus each newly stored successful deployment's commits since the previous success of its stream (repository, kind, name and task; releases one stream) in `data/commits.csv` next to `--data`, written before the deployments so a failed write loses no commits (`history.Validate` checks the deployments first); a success that finished between two stored successes of its stream gets none, with a warning, so no commit counts twice (forsgren#16); a backfilled one, older than the oldest stored, is compared with the success before it, and that oldest stored success waits for a previous and is compared on the run that reads one (`backfill.go`, forsgren#66; [docs/data-files.md, Collecting deployments](docs/data-files.md#collecting-deployments-collect)); and each repository's `failure` issues updated since its read mark in `data/failures_read.csv` less a day (`issuesSince`, `failuresread.go`, forsgren#67), or, before its first read, in the last `history_days` (365 by default, forsgren#57), the new or changed ones appended to `data/failures.csv` next to `--data` (written after the commits and before the deployments; an issue without a readable `failure-start:` in its body is stored with it empty and named on stderr; forsgren#18); and the events of every issue of each repository, whatever its labels, appended to `data/issues.csv` next to `--data` (`issueevents.go`, `Client.Issues` with the failure issues' read mark in `failures_read.csv`; `loadIssueFiles` loads `held.lastEvents`, the newest stored event per issue by time (at the same second created, closed, reopened), before GitHub is asked; the one full read of a repository (`Client.AllIssues`, no `since`, `state=all`, `github.FullReadMaxPages` = 100 pages, decision #109) unless `data/issues_full.csv` (`history.LoadFullAt`/`SaveFullAt`, `held.full`) holds it, noted by `held.noteFull` only after the store and not when the read stopped at its cap (`held.partial`, with a warning on stderr), a bad mark refusing the run in `loadMarks`; created at `created_at`, closed at `closed_at` with `state_reason`, reopened at the run's time `Now` when the issue is open and its last stored event is a close, decisions #100 and #101; written after the failure issues and before the deployments; the known limits are in [docs/data-files.md, Issue events](docs/data-files.md#issue-events-forsgren76); forsgren#76); and the bug flags of each repository (`bugflags.go`, forsgren#126): `readBugs` loads the stored `data/issue_bugs.csv` (refusing the repository before GitHub is asked when it cannot be read), then `Client.BugIssues` lists the issues labelled `bug` (`labels=bug&state=all`, no `since`, `FullReadMaxPages`), `bugFlags` stores each as `bug=true` and, through `lostLabel`, each stored bug no longer listed as `bug=false`, unless the list stopped at the cap, when it keeps the stored flags and warns on stderr (known limit: the Open bugs cell is not marked incomplete, forsgren#140); a refused list or an unwritable file fails the repository, written after the issue events (`readIssues` gathers the failure issues, events and bug flags). `metrics.yml` runs it daily.
- `internal/metrics/` — the DORA numbers, pure functions of the config's projects, the history records, stored commits or failure issues and a render time passed in: `DeploymentFrequency` (successes in the last 7, 30 and 180 days, the latest date, and one of the six DORA Quick Check bands from `BandOf`, by average time between deployments on lead time's edges: the 30-day count decides, the 180-day count only when the 30 days hold none; shown in its table cell with the deciding count by `Frequency.Cell`, forsgren#16 step 6, and the weekend count in the next column by `Frequency.WeekendCell`, forsgren#124; with `Weekend30` and `Weekend180`, the successes of the last 30 and of the last 180 days created on a UTC Saturday or Sunday (`isWeekend`), counted in `Frequency.add` with the same window test as `Last30` and `Last180`, so each is at most its count; `shown()` is the pair of counts (`windowCounts`) of the window the frequency cell shows, 30 days, or 180 when the 30 hold none, and `last30Counts()` the pair of the last 30 days; `Cell` ends with the deciding count alone, and the weekend count has its own column, `WeekendCell` (always a number, `0` when there are none, forsgren#124, decision #129; forsgren#115 put it in the cell and decision #121 ruled no sixth column, which #124 overruled); the scoring view does not show it), and `LeadTimes` (forsgren#16: per project, the commits deployed in the last 30 days, each from author date to deployment, a negative one counted as 0; their median, the mean of the two middle ones for an even count, and their count; the six DORA bands of `LeadTimeBandOf`, a month being 30 days; shown by `LeadTime.Cell`, or "No lead time yet"), and `RecoveryTimes` (forsgren#17: per project, from the stored deployments only, each run of failures of a stream (collect's stream: repository ignoring case, kind, name and task; releases one stream) timed from its first failure's `created_at` to the next success's, one recovery per run, counted when the success is in the last 30 days; their median and count, banded by `LeadTimeBandOf`, since DORA's Quick Check gives failure recovery lead time's six answers; a run with no success yet counted as not recovered yet, whatever its age, never in the median; shown by `Recovery.Cell`, the runs not recovered yet as "N recoveries not completed yet" (decision #35), or "No failed deployments"), and `ChangeFailRates` (forsgren#18: per project, the final deployments (success, failure) of the last 30 days, and the failed changes: per repository the larger of its failed deployments and its `failure` issues opened in the window, so an issue about a failed deployment never counts twice, added up and capped at the deployments; the rate in whole percent rounded down; banded by `ChangeFailBandOf`, the nearest of the six labels of the Quick Check's change fail rate scale, 0% to 100% in steps of 20, a halfway rate the higher; shown by `ChangeFailRate.Cell`, or "No deployments"), and `ReworkRates` (forsgren#39, `rework.go`, the table's fifth column: per project, the successful deployments of the last 30 days that are rework, each counted once: the first success of its stream after a failed deployment, or one created while a `failure` issue of its repository was open (opened at or before it, closed after it or not yet); a service's row has no issues, so only the first applies; the rate in whole percent rounded down, banded by `ChangeFailBandOf` since DORA's Quick Check scales rework rate on the same six labels as change fail rate; shown by `ReworkRate.Cell`, or "No successful deployments"); `IssueDays(events, now, days)` (`issuedays.go`, forsgren#76) is the days page's rows (30 days, `issueDays` in `render.go`, forsgren#123, #128) and the day part of the issues page's: the last `days` UTC calendar days before today, newest first, today left out, a day with no events a zero row, all repositories together, `New` the `created` events and `Completed`, `NotPlanned` and `Duplicate` the `closed` events with that reason and `Other` the ones with no reason or one forsgren does not know, so every close lands in exactly one column (`closedColumn`, decision #107; a reopened event counts nowhere), and `Open` the issues open at the end of the day (`Total` up to 0.8.4): the per-event `openDelta` (+1 created, +1 reopened, -1 closed, whatever the issue and whether or not it has a created event, so the order of the lines does not matter, forsgren#122), summed per row by `periodChanges` and `addUp` from the issues open when the oldest row begins, and shown as calculated, a negative one included; `Total` the issues created up to the end of the day, by `createdDelta` (+1 per created event, nothing else, so a reopen adds none and an issue with no stored created event none), summed the same way, and `IssueDay.OpenShare` Open out of Total as a whole percent rounded down, "—" when Total is 0, so it can exceed 100% on incomplete history (forsgren#134); `bugDelta` (`openDelta` for an event whose issue carries the bug label, `IssueEvent.Bug`, else nothing), summed the same way into `IssueDay.OpenBugs` (forsgren#126); and `IssueDay.OpenChange`/`OpenBugsChange`, how much the count moved over each row's period (the net change `periodRows` already adds up, so the oldest row of a kind is compared with the count at the start of its period), read as `Trend` (`TrendFlat`, `TrendUp`, `TrendDown`) by `OpenTrend()`/`OpenBugsTrend()` through `trendOf` (forsgren#126, forsgren#114); `IssueMonths`/`IssueMonthRows`/`IssueYearMonths`, `IssueYears`/`IssueYearRows`, `IssueWeeks`, `IssueWeekDays` (`issuemonths.go`, `issueyears.go`, `issueweeks.go`, forsgren#89, #125, decision #118) are the same counts per complete UTC calendar month (`IssueMonthRows` back to the oldest event, the current month left out; `IssueYearMonths` is those rows cut at January of the current year, so none in January), per complete UTC calendar year (`IssueYearRows`: every year before the current one back to the year of the oldest event, a year with no events a zero row, its Open the issues open at the end of 31 December), per complete Monday-to-Sunday week touching the current month (Sunday on or after the 1st, Monday before the current week; the current week is not a row) and per day of the current week up to yesterday, sharing `count`, `periodChanges` and `addUp` (`periodRows` adds up the `runningCounts`, one `runningCount` of delta and column each for Open and Total), the period functions (`dayRow`, `weekRow`, `monthRow`, `yearRow`) counting back and leaving the bounds to `rowBack` (`issuedays.go`), and `oldestAt` (the oldest event's time, which `IssueMonthRows` and `IssueYearRows` reach back to; `issuedays.go`), and `IssueRows` (`issuerows.go`) joins them as `IssueRow{Kind, IssueDay}` with `KindDay`, `KindWeek`, `KindMonth` or `KindYear`, days then weeks then the current year's months then the earlier years; recovery time and rework rate share the grouping by stream and the walk of a stream's runs of failures (`stream.go`). The numbers view's cells (`numbercell.go`, forsgren#46) are `NumberCell()` on each: the number only, no band: the last 30 days' successful deployments (0 if none), the weekend deployments among them as `WeekendNumberCell()` (from `last30Counts()`, forsgren#124), the median lead time and recovery time as `shortDuration` (`-` without commits or a completed recovery), and the change fail and rework rates as "14%" (`-` without deployments or successful ones).

## Build and quality gates

- **`./FBP.sh "<message>"`** (FBP = FullBuildAndPush) — the local run: `gofmt -w` → `./sfl.sh pre` → `./Scripts/build_site.sh` → `./sfl.sh post` → commit, and push only when everything is green. A run that ends with exit 0 without reaching its last statement (an unbound variable under bash 3.2) is reported as `Aborted ❌` and exits 1 (forsgren#136). An ordinary red still commits locally with the subject `*** RED ****`; a secret-class red commits nothing. `./FBP.sh --no-commit` runs the gates and the build only.
- **Exit-trap completion** (forsgren#136, #137): a script under `set -e` with a top-level EXIT trap sets `COMPLETED=1` as its last statement and the trap turns an exit of 0 without it into exit 1, because bash 3.2 ends such a script with status 0 on an unbound variable; `Scripts/check_exit_trap_completion.sh` (self-test `test_check_exit_trap_completion.sh`) reads the source, `Scripts/test_exit_trap_completion_behaviour.sh` injects an abort into the real scripts. A new `set -e` script with a trap needs the idiom.
- **`./sfl.sh pre|post`** — the gates of one phase, dispatched from `Scripts/gate_report_order.txt` (`label|script|phase|class`). Every gate is check-only here, as in CI, except npm audit's one-shot `npm audit fix` heal, whose lockfile change rides into the commit (CI turns that heal red).
- **`./Scripts/build_site.sh [out-dir]`** — builds `./cmd/forsgren` into `.build/bin/` and renders the site (default `.build/site`); writes the page count to `.build/site-page-count.log` only on full success.
- **`Scripts/fbp_agent_friend.sh "<message>"`** — FBP.sh under the agent-Friend commit identity, for the subagent loop.
- **CI** — `.github/workflows/quality.yml`, on every push to `main`, every pull request into `main` and by hand, on GitHub's hosted `macos-latest`: `Scripts/install_tools.sh` and `npm ci`, then `Scripts/run_ci_phase.sh pre` → `Scripts/build_site.sh` → `Scripts/run_ci_phase.sh post`, the same order-file rows as sfl, check-only. A `pull_request` trigger is allowed only on a workflow whose every job runs on a GitHub-hosted image label (`ubuntu-*`, `windows-*`, `macos-*`), never with a self-hosted runner; `Scripts/check_workflow_triggers.sh` is red otherwise. Never `pull_request_target`. `Scripts/test_quality_trigger_scope.sh` pins Quality's triggers and its `macos-latest`. See [docs/ci.md](docs/ci.md).
- **`.github/workflows/metrics.yml`** — the reusable workflow (`workflow_call` only) an installation's data repository calls daily with one line, `uses: yveshanoulle/forsgren/.github/workflows/metrics.yml@<commit> # vX.Y.Z`, the only version (no inputs): it `go install`s forsgren from its own `job.workflow_repository` at its own `job.workflow_sha` (checked as one owner/name and 40 hex first; `github.*` would be the caller's) on `go.mod`'s toolchain, checks out the caller's repository (pinned `actions/checkout`, `persist-credentials: false`), runs `forsgren init-config --config forsgren.config.yml` (a created starter is committed alone as `github-actions[bot]` and pushed to the branch the run is on, the token in git's environment only; a kept file exits 0 before any branch logic; the job has no permissions block and takes the caller's grants, `contents: write` among them, plus the optional `pull-requests: read`, which it never demands: a called workflow that asks for more than its caller grants stops the run, forsgren#40) and runs `forsgren check-config --config forsgren.config.yml` on it, failing the job with check-config's message (logged between `::stop-commands::<random token>` and `::<token>::`, so it never runs as a workflow command, and written to `$GITHUB_STEP_SUMMARY` after a cross mark) when the file is invalid, then runs `forsgren collect --config forsgren.config.yml --data data/deployments.csv` with the optional `FORSGREN_TOKEN` secret (`required: false`, passed by name by the caller, in that step's `env:` only; its output logged between `::stop-commands::` and its end like check-config's, its exit status kept as the output `status`), commits a changed `data/` alone as `github-actions[bot]` and pushes it like the starter (a branch that moved fails with an `::error`, never a rebase or force), looks up forsgren's latest release and then Dependabot's waiting pull request for it with the job's token as `GITHUB_TOKEN` (a failed lookup, a 403 included, is an empty output and a `check` of `no-access`, `rate-limited` or `failed`, never a failed job; forsgren#40), renders (`--config`, `--data data/deployments.csv`, and `--latest` and `--waiting-pr` when it found them), writes the run's job summary (`forsgren run-summary` appended to `$GITHUB_STEP_SUMMARY`, never failing the run), deploys to the caller's GitHub Pages, and last fails the job when collect failed; one run at a time per caller repository (`concurrency` on `github.repository`, `cancel-in-progress: false`). Nothing here runs it; `Scripts/test_metrics_workflow.sh` pins its shape. See [docs/configuration.md, Running forsgren](docs/configuration.md#running-forsgren).

Private names: this repository is public, so no tracked or untracked (not ignored) file or path may name a private repository. `Scripts/check_private_names.sh` (secret-class, PRE) searches `git ls-files` and `git ls-files -o --exclude-standard` for the names in `~/.config/forsgren/private-names` (or `FORSGREN_PRIVATE_NAMES_FILE`), locally, and in CI for the newline-separated Actions secret `FORSGREN_PRIVATE_NAMES`, which `quality.yml` passes to the PRE step; no list at all, an env list with no names, or a missing names file is exit 2, while a local names file that exists but holds no names passes with `0 names searched`. The local file is the source of truth; the Actions secret and the Dependabot secret of the same name are synchronized copies, never edited on their own: after changing the file, run `./Scripts/sync_private_names_secrets.sh` by hand (needs the maintainer's `gh` login), which sets both. An external fork pull request receives neither secret, so the gate fails there (exit 2, no list); that is intended: CI always fails without the secret or with an emptied one. `FBP.sh` also refuses a commit message that names a private name, first of all (`Scripts/check_private_names.sh --message <file>`, same list and matching, message via a temp file; with no list or an empty one it passes): no commit, no gate run, one `❌` line that never holds the name or the message, exit 1. Locally, `FBP.sh` creates an empty list file when none exists (`Scripts/ensure_private_names_file.sh`), so the gate passes with `0 names searched`; CI never does. Never write a real private name in a file, test, comment or commit: use made-up names such as `acme-secret-repo`, and say "another estate repository" for a source repository.

Adding a gate: write the script and its self-test, give each a row in the order file at its canon position, add any Homebrew tool it needs to `Scripts/required_tools.txt`, describe it in [docs/quality-gates.md](docs/quality-gates.md), and keep `Scripts/test_sfl_drives_from_order_file.sh` green (every `Scripts/test_*.sh` must be declared). [docs/development.md](docs/development.md) explains FBP.sh, sfl.sh and the order file.

## Code Health (CodeScene MCP), for every Go change

Adopted from another estate repository by Yves on 2026-10-02. An in-session check, deliberately not an sfl or CI gate.

- **Before the FBP of a Go change**, review the changed files with the CodeScene MCP (`code_health_review`, or `analyze_change_set` for several). Report each changed file's score in the hand-off.
- **Floor 9.0:** every Go file stays at 9.0 or above. Warn the moment a change would drop a file below it, and fix it before the FBP.
- **Scoreboard and ratchet:** [codescene-scores.json](codescene-scores.json) holds a row per Go file. `minScore` is the score minus 0.1 for a file below 10 (never below 9.0), and exactly 10.0 for a file at 10.0. Never drop a file below its `minScore`; lift it when a score improves. Update the rows of every reviewed file at each hand-off, and add a row for every new Go file.
- **Rules:** [.codescene/code-health-rules.json](.codescene/code-health-rules.json) puts the cyclomatic-complexity warning at 7 for all Go code, tests included, mirroring `.golangci.yml`'s gocyclo (min-complexity 6, tests included). Change both together.
- **On a Mac without the CodeScene MCP**, say so in the hand-off instead of a score. Never report a score from memory.

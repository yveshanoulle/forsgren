# CLAUDE.md — forsgren

Guidance for Claude Code in this repository.

## What this repo is

forsgren measures the five DORA metrics for a set of GitHub repositories from
GitHub data, and publishes them as a small static page (see
[README.md](README.md)).
It is written in Go: one module, `github.com/yveshanoulle/forsgren`.

## Layout

- `cmd/forsgren/` — the composition root; thin. `forsgren render --out <dir> [--config <path>] [--data <path>]` writes the site; with a config that lists no projects the page shows a how-to, and with the history as well it shows each project's deployment frequency and, from `commits.csv` next to `--data` (missing is none, unknown or malformed fails the render), its lead time for changes (`internal/metrics`, forsgren#16), and from the history its failed deployment recovery time (forsgren#17), and from the history with `failures.csv` next to `--data` (missing is none, unknown or malformed fails the render) its change fail rate (forsgren#18), and from the same files its deployment rework rate (forsgren#39); `render --latest <version>` makes the footer name a newer forsgren release, and `forsgren latest-release` (`latest.go`) prints forsgren's own latest release for it, silent and exit 0 when the lookup fails (forsgren#40), and `render --waiting-pr <number>` with `forsgren waiting-pull-request --version <x.y.z>` (`waiting.go`: the open pull requests of `GITHUB_REPOSITORY` with the job token, `github.ForsgrenBump`) name Dependabot's open pull request for it instead of "is available"; a 403 (no `pull-requests: read`) or any failure prints nothing and exits 0, and with `--status <path>` writes how it went (`ok`, `no-access`, `rate-limited` for GitHub's rate limit, which `OpenPullRequests` keeps as `ErrRateLimit`, never `ErrPullRequestsDenied`, or `failed`); `render --waiting-pr` below 1 is a usage error, and a negative `SOURCE_DATE_EPOCH` fails the render; `forsgren run-summary` (`summary.go`) prints the run's job summary markdown from `--latest`, `--waiting-pr`, `--pr-check` and `--repository` (the pull request is linked: a run page is private, unlike the page), and the workflow appends it to `$GITHUB_STEP_SUMMARY` without ever failing the run (forsgren#40).
- `internal/config/` — `Load` reads and validates an installation's `forsgren.config.yml` (format version 1, strict YAML via `go.yaml.in/yaml/v3`; the optional per-repository `label` or `services` (task → label) name the page's sub-rows, `labels.go`, forsgren#38); the optional top-level `view:` (`standard` or `numbers`, `Config.View` as written, empty when absent, `checkView` in `validate.go`; the root page follows it, forsgren#46); `forsgren check-config --config <path>` runs it, and `forsgren init-config --config <path>` writes the embedded starter (`starter.yml`) when the file is missing and keeps an existing one. Fixture configs only under `internal/config/testdata/`.
- `internal/history/` — the history format v1 (`data/deployments.csv`: a version line, a column line, one CSV line per deployment; README, History): `Load` reads it, `Append` creates it or appends only the deployments not yet there (key: repository, compared ignoring case, kind, ID), and refuses an unknown version or a malformed line untouched; `Validate` is its record check alone, writing nothing. `collect` appends to it; `render --data` reads it. Next to it the commits format v1 (`data/commits.csv`, one line per commit per deployment, for lead time, forsgren#16): `LoadCommits` and `AppendCommits`, the same rules (key: the deployment's key plus the SHA). And the failures format v1 (`data/failures.csv`, one line per state of a `failure`-labelled issue: repository, issue number, opened_at, closed_at and failure_start, the last two possibly empty; for change fail rate, forsgren#18): `LoadFailures` gives each issue once, as its newest line says, and `AppendFailures` appends a line when an issue (key: `IssueKey`, repository ignoring case and number, which collect keys the issues it holds by too) differs from its newest line (`Failure.Revises`), so a closed or reopened issue is written again (the format's `revises`). The files share one generic append-only CSV layer (`file.go`, `append.go`: a `format` per file). `Record.Stream` and `Chronological` (`stream.go`) are the stream and the order of deployments that `collect` and recovery time share (repository ignoring case, kind, name and task, releases one stream; created_at, then ID).
- `internal/github/` — the small GitHub REST client `collect` reads with (standard library only): deployments and their statuses, the default branch, a workflow's runs, releases, a tag's commit, a repository's open pull requests (`OpenPullRequests`, a 403 named as the missing `pull-requests: read`, `ErrPullRequestsDenied`; `ForsgrenBump` finds Dependabot's bump of forsgren's pin to exactly a version by its author and head branch, never its title, a temporary heuristic for the template's dependabot.yml (forsgren#42); forsgren#40), a repository's latest release (`LatestRelease`, no `Authorization` header when the token is empty, forsgren#40), and the commits between two SHAs (`Compare`, `compare/{base}...{head}`, oldest first, cut at the page limit or below `total_commits`; a base that is not an ancestor is `ErrNotAncestor`, a 404 or 422 `ErrMissingCommit`, both naming the two SHAs; forsgren#16; `collect` calls it); the issues labelled `failure` of a repository updated since a time (`FailureIssues`, `issues?labels=failure&state=all&since=`, pull requests left out, every page up to the limit; forsgren#18), each with its number, `created_at`, `closed_at` and the record block of its body (`failure-start:`, `failed-build:`, `fixed-build:` lines; a time it cannot read is zero); the token as a Bearer header only, `Link: rel="next"` pages up to a page limit, errors that name the repository (a 404 or 422 for a release's tag names the tag as missing, `ErrMissingTag`). Tests use `httptest` with fixtures in `testdata/`; they never touch the network.
- `internal/collect/` — `forsgren collect --config <path> --data <path>` (`cmd/forsgren/collect.go`, token from `FORSGREN_TOKEN`): per repository, its rule (`environment=`, `workflow=`, `release`) turned into history records, the final ones appended per repository, plus each newly stored successful deployment's commits since the previous success of its stream (repository, kind, name and task; releases one stream) in `data/commits.csv` next to `--data`, written before the deployments so a failed write loses no commits (`history.Validate` checks the deployments first); a success that finished after a newer success of its stream was stored gets none, with a warning, so no commit counts twice (forsgren#16; README, Collecting deployments); and each repository's `failure` issues updated in the last 90 days, the new or changed ones appended to `data/failures.csv` next to `--data` (written after the commits and before the deployments; an issue without a readable `failure-start:` in its body is stored with it empty and named on stderr; forsgren#18). `metrics.yml` runs it daily.
- `internal/metrics/` — the DORA numbers, pure functions of the config's projects, the history records, stored commits or failure issues and a render time passed in: `DeploymentFrequency` (successes in the last 7, 30 and 180 days, the latest date, and one of the six DORA Quick Check bands from `BandOf`, by average time between deployments on lead time's edges: the 30-day count decides, the 180-day count only when the 30 days hold none; shown in its table cell with the deciding count by `Frequency.Cell`, forsgren#16 step 6), and `LeadTimes` (forsgren#16: per project, the commits deployed in the last 30 days, each from author date to deployment, a negative one counted as 0; their median, the mean of the two middle ones for an even count, and their count; the six DORA bands of `LeadTimeBandOf`, a month being 30 days; shown by `LeadTime.Cell`, or "No lead time yet"), and `RecoveryTimes` (forsgren#17: per project, from the stored deployments only, each run of failures of a stream (collect's stream: repository ignoring case, kind, name and task; releases one stream) timed from its first failure's `created_at` to the next success's, one recovery per run, counted when the success is in the last 30 days; their median and count, banded by `LeadTimeBandOf`, since DORA's Quick Check gives failure recovery lead time's six answers; a run with no success yet counted as not recovered yet, whatever its age, never in the median; shown by `Recovery.Cell`, the runs not recovered yet as "N recoveries not completed yet" (decision #35), or "No failed deployments"), and `ChangeFailRates` (forsgren#18: per project, the final deployments (success, failure) of the last 30 days, and the failed changes: per repository the larger of its failed deployments and its `failure` issues opened in the window, so an issue about a failed deployment never counts twice, added up and capped at the deployments; the rate in whole percent rounded down; banded by `ChangeFailBandOf`, the nearest of the six labels of the Quick Check's change fail rate scale, 0% to 100% in steps of 20, a halfway rate the higher; shown by `ChangeFailRate.Cell`, or "No deployments"), and `ReworkRates` (forsgren#39, `rework.go`, the table's fifth column: per project, the successful deployments of the last 30 days that are rework, each counted once: the first success of its stream after a failed deployment, or one created while a `failure` issue of its repository was open (opened at or before it, closed after it or not yet); a service's row has no issues, so only the first applies; the rate in whole percent rounded down, banded by `ChangeFailBandOf` since DORA's Quick Check scales rework rate on the same six labels as change fail rate; shown by `ReworkRate.Cell`, or "No successful deployments"); recovery time and rework rate share the grouping by stream and the walk of a stream's runs of failures (`stream.go`). The numbers view's cells (`numbercell.go`, forsgren#46) are `NumberCell()` on each: the number only, no band: the last 30 days' successful deployments (0 if none), the median lead time and recovery time as `shortDuration` (`-` without commits or a completed recovery), and the change fail and rework rates as "14%" (`-` without deployments or successful ones).
- `internal/page/` — the page renderer: `Data.Rows`, one table (forsgren#38), the five metrics as columns and as rows `Table(metrics.Rows(...))`, each project's total then its label rows (`metrics.Rows`, `internal/metrics/rows.go`, each row counted by the five metric functions over its own data; short cells from `Cell`, `cell.go`), a link under it to `legend.html`, the second page, which holds the legend of the bands (`templates/pages/legend.html`, static, with a link back to the table; forsgren#39), project names, labels and numbers only, and the render time in the footer on every run, with rows or without, as "Calculated at 2026-10-03 12:00 UTC" (UTC to the minute, passed in as `now` is, or pinned by `SOURCE_DATE_EPOCH`, which `Scripts/test_build_site.sh` sets; forsgren#41, reversing #28), and, for a config with no projects, a how-to with an example config in place of the table (forsgren#41), never a repository, SHA or commit message; `html/template` files embedded with `//go:embed`, shared chrome in `templates/layout/*.html` (no header: the table page opens with the table, under a visually hidden h1 "Forsgren <version>: the five DORA metrics", and the legend page carries the paragraph on where each metric comes from, forsgren#41; the footer: Forsgren linked to its repository, the version, what it is, "Calculated at ...", " · <version> is available", or "is waiting in pull request #N (merge it to update)" when `Data.WaitingPR` is set, when `Data.Latest` is a newer release (`Data.Update`, `newer`, `ReleaseVersion`: numbers compared as numbers; forsgren#40), forsgren#41; no Install link, forsgren#45) (one `{{define}}` each), one file per page in `templates/pages/*.html`, `styles.css`, the hand-authored `required-pages.json`, golden files in `testdata/` (placeholder, legend, no-projects, no-data, frequency, lead time, recovery, change fail rate, labels; `Scripts/check_golden_pages.sh` gates each); and the views (forsgren#46, `page.go`: `views`, `pageData`, whose `Base` prefixes the links to `styles.css` and `legend.html`, `../` one folder down, and whose `View` shows the switch, `templates/layout/switch.html`, in the table's caption after its title, a `<span id="metrics-caption">` that names the table (`aria-labelledby`) and its region, forsgren#51): `PageNames` and `WriteSite` also give `standard/index.html` and `numbers/index.html`, both rendered from `index.html` (the table in `templates/layout/table.html`, the numbers view on `NumberCell`s, a row with no deployments five cells there; goldens `standard*`/`numbers*`), the root page following `Data.View` (`cfg.View`, set by `pageData` in `render.go`; the switch's links are `{{.Base}}`-relative; empty `View` is the plain root, byte-identical, with no switch); `required-pages.json` and `test_required_pages_covers_site.sh` know folders (`standard/index.html` is `/standard/`).
- `Scripts/` — the gates, their self-tests and the build script; `Scripts/gate_report_order.txt` declares every gate.
- `CODE_OF_CONDUCT.md` — the Contributor Covenant 3.0, reports to conduct@hanoulle.be; README links it, and `Scripts/check_community_files.sh` keeps both true, and the same for `SECURITY.md` and its private reporting route (forsgren#43, #44).
- `.build/` — build output, never committed: `.build/bin/forsgren`, the generated site in `.build/site/`, the counts sinks.

## Build and quality gates

- **`./FBP.sh "<message>"`** (FBP = FullBuildAndPush) — the local run: `gofmt -w` → `./sfl.sh pre` → `./Scripts/build_site.sh` → `./sfl.sh post` → commit, and push only when everything is green. An ordinary red still commits locally with the subject `*** RED ****`; a secret-class red commits nothing. `./FBP.sh --no-commit` runs the gates and the build only.
- **`./sfl.sh pre|post`** — the gates of one phase, dispatched from `Scripts/gate_report_order.txt` (`label|script|phase|class`). Every gate is check-only here, as in CI, except npm audit's one-shot `npm audit fix` heal, whose lockfile change rides into the commit (CI turns that heal red).
- **`./Scripts/build_site.sh [out-dir]`** — builds `./cmd/forsgren` into `.build/bin/` and renders the site (default `.build/site`); writes the page count to `.build/site-page-count.log` only on full success.
- **`Scripts/fbp_agent_friend.sh "<message>"`** — FBP.sh under the agent-Friend commit identity, for the subagent loop.
- **CI** — `.github/workflows/quality.yml`, on every push to `main`, every pull request into `main` and by hand, on GitHub's hosted `macos-latest`: `Scripts/install_tools.sh` and `npm ci`, then `Scripts/run_ci_phase.sh pre` → `Scripts/build_site.sh` → `Scripts/run_ci_phase.sh post`, the same order-file rows as sfl, check-only. A `pull_request` trigger is allowed only on a workflow whose every job runs on a GitHub-hosted image label (`ubuntu-*`, `windows-*`, `macos-*`), never with a self-hosted runner; `Scripts/check_workflow_triggers.sh` is red otherwise. Never `pull_request_target`. `Scripts/test_quality_trigger_scope.sh` pins Quality's triggers and its `macos-latest`. See README, CI.
- **`.github/workflows/metrics.yml`** — the reusable workflow (`workflow_call` only) an installation's data repository calls daily with one line, `uses: yveshanoulle/forsgren/.github/workflows/metrics.yml@<commit> # vX.Y.Z`, the only version (no inputs): it `go install`s forsgren from its own `job.workflow_repository` at its own `job.workflow_sha` (checked as one owner/name and 40 hex first; `github.*` would be the caller's) on `go.mod`'s toolchain, checks out the caller's repository (pinned `actions/checkout`, `persist-credentials: false`), runs `forsgren init-config --config forsgren.config.yml` (a created starter is committed alone as `github-actions[bot]` and pushed to the branch the run is on, the token in git's environment only; a kept file exits 0 before any branch logic; the job has no permissions block and takes the caller's grants, `contents: write` among them, plus the optional `pull-requests: read`, which it never demands: a called workflow that asks for more than its caller grants stops the run, forsgren#40) and runs `forsgren check-config --config forsgren.config.yml` on it, failing the job with check-config's message (logged between `::stop-commands::<random token>` and `::<token>::`, so it never runs as a workflow command, and written to `$GITHUB_STEP_SUMMARY` after a cross mark) when the file is invalid, then runs `forsgren collect --config forsgren.config.yml --data data/deployments.csv` with the optional `FORSGREN_TOKEN` secret (`required: false`, passed by name by the caller, in that step's `env:` only; its output logged between `::stop-commands::` and its end like check-config's, its exit status kept as the output `status`), commits a changed `data/` alone as `github-actions[bot]` and pushes it like the starter (a branch that moved fails with an `::error`, never a rebase or force), looks up forsgren's latest release and then Dependabot's waiting pull request for it with the job's token as `GITHUB_TOKEN` (a failed lookup, a 403 included, is an empty output and a `check` of `no-access`, `rate-limited` or `failed`, never a failed job; forsgren#40), renders (`--config`, `--data data/deployments.csv`, and `--latest` and `--waiting-pr` when it found them), writes the run's job summary (`forsgren run-summary` appended to `$GITHUB_STEP_SUMMARY`, never failing the run), deploys to the caller's GitHub Pages, and last fails the job when collect failed; one run at a time per caller repository (`concurrency` on `github.repository`, `cancel-in-progress: false`). Nothing here runs it; `Scripts/test_metrics_workflow.sh` pins its shape. See README, Running forsgren.

Adding a gate: write the script and its self-test, give each a row in the order file at its canon position, add any Homebrew tool it needs to `Scripts/required_tools.txt`, describe it in README's Quality gates, and keep `Scripts/test_sfl_drives_from_order_file.sh` green (every `Scripts/test_*.sh` must be declared). README's "Working on forsgren" explains FBP.sh, sfl.sh and the order file.

## Code Health (CodeScene MCP), for every Go change

Adopted from MenoPower by Yves on 2026-10-02. An in-session check, deliberately not an sfl or CI gate.

- **Before the FBP of a Go change**, review the changed files with the CodeScene MCP (`code_health_review`, or `analyze_change_set` for several). Report each changed file's score in the hand-off.
- **Floor 9.0:** every Go file stays at 9.0 or above. Warn the moment a change would drop a file below it, and fix it before the FBP.
- **Scoreboard and ratchet:** [codescene-scores.json](codescene-scores.json) holds a row per Go file. `minScore` is the score minus 0.1 for a file below 10 (never below 9.0), and exactly 10.0 for a file at 10.0. Never drop a file below its `minScore`; lift it when a score improves. Update the rows of every reviewed file at each hand-off, and add a row for every new Go file.
- **Rules:** [.codescene/code-health-rules.json](.codescene/code-health-rules.json) puts the cyclomatic-complexity warning at 7 for all Go code, tests included, mirroring `.golangci.yml`'s gocyclo (min-complexity 6, tests included). Change both together.
- **On a Mac without the CodeScene MCP**, say so in the hand-off instead of a score. Never report a score from memory.
